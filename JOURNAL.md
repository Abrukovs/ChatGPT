# Journal and result settlement

## 1. Required record fields
Each prediction should be stored as one durable record with, at minimum:

| Field | Meaning |
|---|---|
| prediction_id | Stable unique identifier; use it to prevent duplicates |
| selected_at_riga | Date/time the prediction was selected, Europe/Riga |
| sport | Hockey, basketball or tennis |
| competition | League or tournament |
| event | Match or fixture |
| scheduled_start_riga | Scheduled start time, Europe/Riga |
| market | Market name and settlement basis |
| line | Exact selected line |
| reference_odds | Approximate decimal odds or quoted range at selection |
| odds_status | Confirmed at named bookmaker, or approximate/unverified |
| odds_source | Source or bookmaker examples, if available |
| odds_checked_at_riga | Time price was checked |
| estimated_probability_pct | Original estimated chance of success |
| implied_probability_pct | 100 divided by reference decimal odds, before margin adjustment |
| grade | A, B+, B; use PASS in the run report when no pick is selected |
| rationale | Concise reasons for the selection |
| risks | Main failure modes and unresolved uncertainties |
| user_actual_odds | Separate field, filled only if the user later reports their price |
| result_status | Pending, Win, Loss, Push/Refund, Void/Cancelled, Unable to verify |
| final_score | Final score from a reliable source |
| settled_at_riga | Date/time result was checked |
| result_source_url | Link to the result source |
| settlement_notes | Explanation for unusual settlement rules or uncertainty |

Additional fields can be added if useful, but should not replace these.

## 2. Immutability rule
Once a pick is recorded, never silently overwrite its original event, market, line, reference odds, estimated probability, grade or rationale. If a correction is necessary, preserve the original values and add a correction note with timestamp and reason. A later user-reported price belongs in user_actual_odds, not in reference_odds.

## 3. Daily settlement-first process
At the start of every run:
1. Find records from previous days that are still pending.
2. For each, locate the final score in a reliable source such as an official league, tournament or team site where available.
3. Check the actual market settlement conditions carefully. Examples: regulation only versus overtime included; whether a tennis retirement voids the market; push rules for integer totals/handicaps.
4. Update the original record's result status, final score, settlement timestamp in Riga time, result source URL and notes.
5. If the result cannot be reliably verified, use **Unable to verify**. Do not guess.
6. Only after this process, scan the current slate and record a new selection if one qualifies.

## 4. Duplicate prevention
Before creating a record, search the existing journal for the same prediction_id. Also check whether the same run or event/market has already been recorded. Repeated task runs must not create duplicate rows. Use a stable ID generated by the implementation; if there is no implementation yet, use a deterministic combination of selection date/time, event and market and check it before writing.

## 5. Coda integration and fallback
If Coda actions are available in the current run:
- Use or create a table named **Спортивные прогнозы**.
- Append each new pick as a new row.
- Update results in the original row.
- Check for duplicates before inserting.
- Confirm that the write succeeded before saying the journal was updated.

If Coda is unavailable or a write fails:
- Do not claim the Coda record was saved.
- Output the record as a structured table or CSV row that can be added manually.
- Clearly state the limitation.
- Maintain an accumulating local/exportable journal where the environment supports it.

## 6. Exports and reporting
The accumulated journal should be exportable to CSV and XLSX. Keep one row per prediction and use consistent field names and result statuses. Do not store stake amounts. Preserve source URLs for settled results.

## 7. Performance evaluation
Report outcomes transparently and use an adequate sample size before drawing conclusions. Track wins, losses, pushes/refunds, voids and unverified results separately. Do not count pending or unverified records as wins. Avoid changing the historical grade after the result is known.
